# First-run onboarding

The screens the Sozvon apps show on their very first launch: a welcome, one
question — *what do you have already?* — and a short path from the answer to
where the person meant to be.

| Path | Steps | Ends |
|---|---|---|
| I was invited | link → camera and microphone → ready | in the call |
| I have a server | address → dashboard or room → camera and microphone → ready | on the dashboard, or in the room |
| I want my own | what you need (→ optional VPS guide) → the deploy wizard → done | with the operator password and a first guest link |

The camera and microphone step only appears when there is something to ask:
on Android when the permissions are not granted yet, on Windows only when the
system's privacy settings block the devices (Windows has no permission dialog
to prepare anybody for).

## Boundaries

In scope: the screens above, checking a server before anybody is sent to it,
explaining a permission before the system asks for it, and wrapping the
existing deploy wizard with a checklist before it and a first guest link after
it. Skippable from every screen; shown once; never shown to somebody who
already has a saved server or arrived by a link.

Out of scope, on purpose:

- **The web client.** The device check, the name prompt and the call itself
  are the server's pages, shared with every browser. The onboarding hands over
  to them and stops.
- **The installer.** `contrib/install.sh` and the deploy wizards are reused as
  they are; only what comes before and after them is new.
- **The server.** Nothing here needs a server change. The first guest link is
  made the way the operator dashboard makes one (see `minter.js`).
- **Telemetry.** Whether the onboarding was finished is stored on the device
  and nowhere else.

## One source, two apps

This directory is the only copy under version control. Each app copies it at
build time, the same way both copy `contrib/install.sh`:

- **Android** — the `syncOnboarding` task in `android/app/build.gradle.kts`
  copies it into the app's assets; `OnboardingActivity` shows it in a WebView.
- **Desktop** — `desktop/scripts/sync-onboarding.js` (run before `start`,
  `package` and `dist`) copies it to `desktop/src/renderer/onboarding/`, so it
  counts as one of the app's own pages; `main.js` shows it in place of the
  launcher.

Both copies are git-ignored. Edit here, never there.

## Files

| File | What it is |
|---|---|
| `index.html`, `onboarding.css` | the page and its look: the client's monochrome palette, both themes |
| `app.js` | the screens and their wiring |
| `flow.js` | the decisions — link parsing, step order, progress — with no DOM |
| `i18n.js` | every string, Russian and English |
| `host.js` | the bridge to the app, and a stand-in when the page is opened alone |
| `minter.js` | injected by the app into a hidden page of a freshly installed server, to make the first guest link |
| `mark.svg` | the mark; generated by `contrib/build-mark-assets.py` |

### The bridge

`app.js` talks to `window.SozvonHost` only. Requests are
`SozvonHost.call(method, args)` and always resolve:

| Method | Answer |
|---|---|
| `checkServer {url}` | `{status: ok \| other \| unreachable \| cert \| cert-changed}` |
| `media` | `{state: granted \| prompt \| blocked \| n/a}` |
| `requestMedia` | `{camera, mic}` (Android) |
| `openSettings {which?}` | the app's settings (Android), the privacy page (Windows) |
| `paste` | `{text}` from the clipboard, read only when the button is pressed |
| `deploy` | `{result}` or `{cancelled}`; on the desktop the page is replaced and the answer arrives through `takeDeployResult` on the next load |
| `mint {origin, group, username, password, slug}` | `{ok, url}` or `{ok: false, error}` |
| `copy {text, sensitive}`, `share {text}` | `{ok}` |
| `finish {url, origin, room, hub}` | the app remembers the server, marks the onboarding done and opens it |
| `skip` | the app marks it done and shows its server list |

### The first guest link

A server answers a websocket only from a page of its own origin, and the
onboarding is a page on the device. So the app opens the new server's
`/healthz` in a hidden view — same certificate checks as everything else,
pins included — injects `minter.js` there, and calls `sozvonMint()`. It joins
the operator hub with the password the installer just reported, asks for a
token on a fresh child room exactly as the dashboard's *Create link* does, and
closes the socket. The password is not kept.

## Working on it

Open `index.html` in a browser (any static server will do): with no app around
it, `host.js` answers with plausible made-up results, so every screen can be
reached. `?lang=en` and `?theme=light` pick the language and the theme.

    node --test 'onboarding/test/*.test.js'
